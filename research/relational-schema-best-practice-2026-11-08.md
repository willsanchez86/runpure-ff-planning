# MySQL 8.4 (InnoDB) schema best practice for the nflverse store

Researched 2026-11-08. Sources were fetched that day. MySQL manual pages show no revision date (footer "(c) 2026 Oracle"), so the date of each one is given as "n.d. (8.4 manual, accessed 2026-11-08)". Quotes are under 15 words. Labels: **UNVERIFIED** means no source was found or fetched for the point. **INFERENCE** means my own reasoning. Finding IDs (e.g. F1.3) are used in the rule set at the end.

---

## 1. Entities vs facts; 3NF vs dimensional

- **F1.1** Kimball's four steps are: "Select the business process", "Declare the grain", "Identify the dimensions", "Identify the facts". [Kimball Group, Four-Step Design Process](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/four-4-step-design-process/) (n.d.). *Applies to us:* each nflverse file is a business process. Write down the grain of each table before choosing columns.
- **F1.2** "Declaring the grain means saying *exactly* what a fact table record represents." The most common error is not declaring it at the start. Prefer the "most atomic level". [Kimball, Declaring the Grain](https://www.kimballgroup.com/2003/03/declaring-the-grain/) (2003-03-01). *Applies to us:* player_week grain = one player x season x season_type x week. Play grain = one game_id x play_id. Keep the atomic weekly rows and derive season totals from them.
- **F1.3** A table should hold "only facts of a uniform grain". Daily and yearly data go in separate tables. Facts are numeric measurements and should be additive where possible. Dimensions are "mostly textual". [Kimball, Fact Tables and Dimension Tables](https://www.kimballgroup.com/2003/01/fact-tables-and-dimension-tables/) (2003-01-01). *Applies to us:* never mix season-total rows into player_week. Store counts (yards, attempts), not only rates, so ranges over weeks can be summed.
- **F1.4** Factless fact tables record "dimensional entities coming together at a moment in time". [Kimball, Factless Fact Table](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/factless-fact-table/) (n.d.). *Applies to us:* roster membership (player x team x season[/week]) and injury reports are event or coverage facts, even though they hold few or no measures.
- **F1.5** A degenerate dimension has "no content except for its primary key" and lives in the fact table. [Kimball, Degenerate Dimension](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/degenerate-dimension/) (n.d.). *Applies to us:* play_id and drive number can sit in the play table without their own tables.
- **F1.6** "A dimensional model contains the same information as a normalized model." It is "packaged for ease-of-use". [Margy Ross, Differences of Opinion](https://www.kimballgroup.com/?p=15387) (2004-03-03). *Applies to us:* the choice is about query shape, not lost information. An analytics read workload favours facts plus a few dimensions.
- **F1.7** Under 2NF/3NF, each non-key field is a fact "about exactly the whole key and nothing else". Normalisation prevents "update anomalies". But "no obligation to fully normalize" when performance requires it. [William Kent, A Simple Guide to Five Normal Forms](https://www.bkent.net/Doc/simple5.htm) (CACM Feb 1983). *Applies to us:* keep entity tables (player, team, game) in 3NF. Attributes such as birth_date and draft year belong to player, not to every weekly row.
- **F1.8 INFERENCE.** Proposed split:
  - Dimensions/entities: player (gsis id), team (abbr), game (game_id, from schedules), season. Week is an attribute of game and of fact keys, not its own table.
  - Facts: player_week_stat, team_week_stat, snap_count (player x game), injury_report (player x season x week x team), roster (player x team x season), play (pbp).
  - The source CSVs are already denormalised (names and positions are repeated per row). Keep the descriptive columns your loader needs in staging only. In facts, keep the keys plus measures. Keep one practical denormalisation for the explorer: position at the time of the row, because a player's position can change across seasons.

## 2. Keys

- **F2.1** "A primary key should be defined for each table." With no suitable key, InnoDB makes a hidden 6-byte `GEN_CLUST_INDEX`. [8.4 manual, Clustered and Secondary Indexes](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html) (n.d.). *Applies to us:* every table, staging included, gets an explicit PK.
- **F2.2** Each secondary-index record "contains the primary key columns". "it is advantageous to have a short primary key." [same page](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html). Also: "The primary index of a table should be as short as possible." [8.4 manual, Optimizing Data Size](https://dev.mysql.com/doc/refman/8.4/en/data-size.html) (n.d.). *Applies to us:* a composite natural PK such as (SMALLINT, TINYINT, TINYINT, CHAR(10)) is about 14 bytes. That is acceptable with 1 or 2 secondary indexes. Avoid long VARCHAR PKs.
- **F2.3** InnoDB best practice: use "the most frequently queried column or columns", or auto-increment if there is no obvious PK. [8.4 manual, InnoDB Best Practices](https://dev.mysql.com/doc/refman/8.4/en/innodb-best-practices.html) (n.d.). *Applies to us:* a natural composite PK that leads with the filter columns (season, week) is endorsed.
- **F2.4** InnoDB "automatically extends each secondary index by appending the primary key columns". The optimizer uses those columns. [8.4 manual, Use of Index Extensions](https://dev.mysql.com/doc/refman/8.4/en/index-extensions.html) (n.d.). *Applies to us:* an index on (player_id) on player_week is effectively (player_id, season, season_type, week). It serves player-history lookups without listing those columns.
- **F2.5** A composite natural PK clusters related rows: "rows are ordered, grouped, by user_id inside the primary key B-Tree". The costs are non-sequential inserts, page fragmentation (about 60% larger table in the test) and larger secondary indexes. It is "not a silver bullet". [Yves Trudeau, Percona, Tuning InnoDB Primary Keys](https://www.percona.com/blog/tuning-innodb-primary-keys/) (2018-07-26). *Applies to us:* our loads are bulk and per season, and can be sorted by PK first. That removes the insert-order cost (see F7.3).
- **F2.6** In a warehouse, a dimension PK "cannot be the operational system's natural key". Kimball uses "anonymous integer primary keys", mainly for history tracking (SCD). Date dimensions are exempt. [Kimball, Dimension Surrogate Key](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/dimension-surrogate-key/) (n.d.). *Applies to us, INFERENCE:* we do not track SCD history on player and the gsis id is stable, so natural keys are acceptable. Add a surrogate key only if you merge multiple ID systems (gsis/pfr/espn). A crosswalk table can hold those instead.
- **F2.7** "MySQL requires indexes on foreign keys and referenced keys". The index is created automatically if missing. [8.4 manual, FOREIGN KEY Constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html) (n.d.). Also "define foreign keys on the join columns" with the "same data type in each table". [InnoDB Best Practices](https://dev.mysql.com/doc/refman/8.4/en/innodb-best-practices.html). *Applies to us:* FK columns get indexes either way, so plan them as part of your index budget.
- **F2.8** `foreign_key_checks=0` is meant for reloading tables in a different order and for `LOAD DATA`. But enabling it again "does not trigger a scan". Rows loaded while it was off are never checked. [FOREIGN KEY Constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html). *Applies to us:* if you disable checks, run an explicit orphan check (LEFT JOIN ... IS NULL) before the swap.
- **F2.9** "Partitioned tables using the InnoDB storage engine do not support foreign keys." [8.4 manual, Partitioning Limitations](https://dev.mysql.com/doc/refman/8.4/en/partitioning-limitations.html) (n.d.). *Applies to us:* partitioning by season (for EXCHANGE PARTITION swaps, F7.6) rules out FKs on those tables. You must pick one.
- **F2.10** Kimball: a NULL in a column declared as an FK violates referential integrity. Point unknowns at a special "unknown" row instead. [Thornthwaite, Design Tip #43](https://www.kimballgroup.com/2003/02/design-tip-43-dealing-with-nulls-in-the-dimensional-model/) (2003-02-06). *Applies to us:* in pbp, passer/rusher/receiver IDs are NULL on most plays. Either leave them without an FK (nullable) or accept that NULL FKs are allowed in MySQL but drop out of inner joins. **INFERENCE:** the first option is simpler.

## 3. Data types

- **F3.1** "Use the most efficient (smallest) data types possible." "MEDIUMINT is often a better choice than INT". [Optimizing Data Size](https://dev.mysql.com/doc/refman/8.4/en/data-size.html). Sizes: TINYINT 1, SMALLINT 2, MEDIUMINT 3, INT 4, BIGINT 8, FLOAT 4, DOUBLE 8, DATE 3, DATETIME 5, TIMESTAMP 4 bytes. DECIMAL uses 4 bytes per 9 digits. [8.4 manual, Data Type Storage Requirements](https://dev.mysql.com/doc/refman/8.4/en/storage-requirements.html) (n.d.). Ranges: TINYINT -128..127 (unsigned 0..255), SMALLINT -32768..32767 (unsigned 0..65535). [8.4 manual, Integer Types](https://dev.mysql.com/doc/refman/8.4/en/integer-types.html) (n.d.). *Applies to us:* season SMALLINT UNSIGNED, week TINYINT UNSIGNED. Yardage needs SIGNED SMALLINT, because yards can be negative and season totals can exceed 127. Counts (attempts, targets) fit TINYINT UNSIGNED per week.
- **F3.2** Display width (`INT(11)`) and ZEROFILL are deprecated. UNSIGNED is deprecated for FLOAT/DOUBLE/DECIMAL; use a CHECK constraint instead. `FLOAT(M,D)` is deprecated. [8.4 manual, Numeric Data Type Syntax](https://dev.mysql.com/doc/refman/8.4/en/numeric-type-syntax.html) (n.d.). *Applies to us:* write `INT`, not `INT(11)`. Write `DOUBLE`, never `DOUBLE UNSIGNED` or `FLOAT(7,4)`.
- **F3.3** BOOL/BOOLEAN "are synonyms for TINYINT(1)". TRUE/FALSE are aliases for 1/0. [Numeric Data Type Syntax](https://dev.mysql.com/doc/refman/8.4/en/numeric-type-syntax.html). *Applies to us:* pbp has dozens of 0/1 flags (pass, rush, touchdown...). Declare them `BOOLEAN` (stored as TINYINT, 1 byte). **INFERENCE:** add `CHECK (col IN (0,1))` if you want strictness.
- **F3.4** Floats "are approximate and not stored as exact values". Comparing them as exact values "may lead to problems". DECIMAL is computed to 65-digit precision. [8.4 manual, Problems with Floating-Point Values](https://dev.mysql.com/doc/refman/8.4/en/problems-with-float.html) (n.d.). *Applies to us, INFERENCE:* EPA, WPA, CPOE and air-yards-share are model outputs that nflverse supplies as floating point. DOUBLE stores them without loss, and they are never compared for equality. Use DECIMAL only where exact decimal arithmetic matters (e.g. if you store fantasy scoring weights). Integer stats stay integers.
- **F3.5** CHAR is fixed length and right-padded. VARCHAR uses a "1-byte or 2-byte length prefix plus data". [8.4 manual, CHAR and VARCHAR](https://dev.mysql.com/doc/refman/8.4/en/char.html) (n.d.). CHAR(M) in utf8mb4 can take up to 4M bytes, but the compact row formats "optimize storage for variable-length character sets". [Storage Requirements](https://dev.mysql.com/doc/refman/8.4/en/storage-requirements.html). *Applies to us:* gsis ids like `00-0023459` are fixed-width ASCII. **INFERENCE:** use `CHAR(10) CHARACTER SET ascii COLLATE ascii_bin` for exactly 1 byte/char and byte-exact comparison. **UNVERIFIED:** that every nflverse gsis id is exactly 10 chars. Check with `MAX(LENGTH())` during profiling.
- **F3.6** Indexes are used more efficiently on columns "declared as the same type and size". Comparing utf8mb4 with latin1 "precludes use of an index". [8.4 manual, How MySQL Uses Indexes](https://dev.mysql.com/doc/refman/8.4/en/mysql-indexes.html) (n.d.). *Applies to us:* player_id must have an identical type, charset and collation in every table. The same applies to team abbreviation and game_id.
- **F3.7** The default charset and collation "are utf8mb4 and utf8mb4_0900_ai_ci". [8.4 manual, Server Character Set and Collation](https://dev.mysql.com/doc/refman/8.4/en/charset-server.html) (n.d.). *Applies to us:* names with diacritics or apostrophes work out of the box. `_ai_ci` makes searches accent- and case-insensitive, which suits name search. Keep it for name and text columns and use ascii for codes (F3.5).
- **F3.8** DATE covers 1000-01-01..9999-12-31. TIMESTAMP covers 1970..2038-01-19 UTC and is converted from the session time zone to UTC. DATETIME is not converted. [8.4 manual, DATE, DATETIME, TIMESTAMP](https://dev.mysql.com/doc/refman/8.4/en/datetime.html) (n.d.). *Applies to us:* birth_date and gameday should be DATE. **INFERENCE:** nflverse gametime is US Eastern local time. Store it as DATE + TIME as given, or convert to UTC in the loader and store a DATETIME. Avoid TIMESTAMP because of the 2038 limit and the session-dependent conversion.
- **F3.9** ENUM sorts by index number, not alphabetically. The manual "strongly recommend[s]" against numbers as ENUM values. Storage is 1 byte for up to 255 values. [8.4 manual, The ENUM Type](https://dev.mysql.com/doc/refman/8.4/en/enum.html) (n.d.); [Storage Requirements](https://dev.mysql.com/doc/refman/8.4/en/storage-requirements.html). *Applies to us:* season_type ('REG','POST') fits ENUM well. Position and team are better as short CHAR/VARCHAR codes or lookup tables, because their value sets change. **UNVERIFIED:** whether adding an ENUM member needs a table rebuild. The page did not say.
- **F3.10** "Declare columns to be NOT NULL if possible". It enables "better use of indexes" and saves a bit per column. [Optimizing Data Size](https://dev.mysql.com/doc/refman/8.4/en/data-size.html). In COMPACT/DYNAMIC rows, NULL columns "do not occupy space other than the bit". [8.4 manual, InnoDB Row Formats](https://dev.mysql.com/doc/refman/8.4/en/innodb-row-format.html) (n.d.). Kimball keeps NULL measures, because zero would "skew these aggregated calculations". [Design Tip #43](https://www.kimballgroup.com/2003/02/design-tip-43-dealing-with-nulls-in-the-dimensional-model/). *Applies to us:* key columns are NOT NULL. A stat column should allow NULL where the source means "not applicable" (e.g. a kicking stat for a WR). That keeps AVG() honest and costs only one bit.
- **F3.11** Strict mode (`STRICT_TRANS_TABLES`) is in the default sql_mode. [8.4 manual, FAQ: SQL Modes](https://dev.mysql.com/doc/refman/8.4/en/faqs-sql-modes.html) (n.d.; the page text says "MySQL 8.0", so confirm in 7.1.11). *Applies to us:* keep strict mode on during loads so that bad values raise errors instead of being silently clamped.

## 4. Wide tables (114 and 372 columns)

- **F4.1** The hard limit is 4096 columns. InnoDB allows "1017 columns per table". The row limit is 65,535 bytes. InnoDB rows stored in-page must be "slightly less than 8KB" at a 16KB page. [8.4 manual, Limits on Table Column Count and Row Size](https://dev.mysql.com/doc/refman/8.4/en/column-count-limit.html) (n.d.). *Applies to us:* 372 pbp columns fit the column limit. **INFERENCE:** 114 numeric columns at 8 bytes or less is about 900 bytes per row, far below 8KB.
- **F4.2** "BLOB and TEXT columns only contribute 9 to 12 bytes toward the row size limit". Length bytes of VARCHAR do count. [same page](https://dev.mysql.com/doc/refman/8.4/en/column-count-limit.html). *Applies to us, INFERENCE:* in pbp, declared VARCHAR sizes in utf8mb4 count at up to 4 bytes per char toward 65,535. Size string columns tightly from profiling. Use `TEXT` for `desc` (play description) and use ascii for code columns.
- **F4.3** In DYNAMIC (the default), long variable-length values go "fully off-page", leaving a 20-byte pointer. The longest columns move off-page until the record fits. [InnoDB Row Formats](https://dev.mysql.com/doc/refman/8.4/en/innodb-row-format.html); "InnoDB tables are created using the DYNAMIC row format by default." [Optimizing Data Size](https://dev.mysql.com/doc/refman/8.4/en/data-size.html). *Applies to us:* wide rows still work, but off-page reads cost extra I/O when those columns are selected.
- **F4.4** "it can be beneficial to split into two a table that is scanned very often". [Optimizing Data Size](https://dev.mysql.com/doc/refman/8.4/en/data-size.html). *Applies to us, INFERENCE:* vertical split is optional at our sizes (about 50k pbp rows a season). Splitting player_week into offense, defense and kicking tables on the same PK would cut the explorer's scan width, but it adds joins. Start with one table plus a covering index (F5.3). Split only if EXPLAIN or timing shows a need.
- **F4.5** JSON columns "are not indexed directly". Indexing goes through a generated column. Storage is roughly that of LONGBLOB. [8.4 manual, The JSON Data Type](https://dev.mysql.com/doc/refman/8.4/en/json.html) (n.d.). *Applies to us:* do not put stats you filter or sort on into JSON. JSON suits only rarely used, schema-unstable extras.

## 5. Indexing for the read patterns

- **F5.1** "any leftmost prefix of the index can be used". An index can hold up to 16 columns. A query cannot use the index if its columns are not a leftmost prefix. [8.4 manual, Multiple-Column Indexes](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html) (n.d.). *Applies to us:* put equality columns first (season, season_type), then the range column (week). Because of the prefix rule, a PK of (season, season_type, week, player_id) serves "season X, weeks a..b".
- **F5.2** "create a single composite index" for combined searches, rather than one per column. Indexes "slow down insert and update operations". [Optimizing Data Size](https://dev.mysql.com/doc/refman/8.4/en/data-size.html). *Applies to us:* keep 1 or 2 secondary indexes per fact table. Loads rebuild every index.
- **F5.3** "An index that provides all the necessary results for a query is called a covering index." [How MySQL Uses Indexes](https://dev.mysql.com/doc/refman/8.4/en/mysql-indexes.html). EXPLAIN shows "Using index" for one. [Index Extensions](https://dev.mysql.com/doc/refman/8.4/en/index-extensions.html). *Applies to us, INFERENCE:* the explorer computes fantasy points from about 15 to 20 stat columns. A covering index on those would be wide. At about 6k player-weeks a season, a clustered PK range scan is cheap, so a covering index is likely unnecessary. Measure first.
- **F5.4** Clustering by PK (F2.5) means a range on the leading PK columns reads contiguous pages. [Percona, Tuning InnoDB Primary Keys](https://www.percona.com/blog/tuning-innodb-primary-keys/). *Applies to us:* choose the PK by the dominant query, the season/week range scan. Add a secondary index `(player_id)` for player pages (it is auto-extended, F2.4), and `(position, season)` only if position lives on the fact row.

## 6. Naming

- **F6.1** "Only use letters, numbers and underscores". Use underscores where a space would go, and lowercase. [Simon Holywell, SQL Style Guide](https://www.sqlstyle.guide/) (modified 2026-03-17, CC BY-SA 4.0). *Applies to us:* snake_case everywhere. This matches nflverse column names, so no renaming is needed.
- **F6.2** For tables: "Use a collective name or, less ideally, a plural form". No `tbl` prefix. Columns: "Always use the singular name". Avoid a bare `id` as the primary identifier. [SQL Style Guide](https://www.sqlstyle.guide/). *Applies to us:* e.g. `roster`/`players`/`play_by_play`. Pick one convention and apply it everywhere. **INFERENCE:** singular table names (`player`, `game`) are also common practice. Consistency matters more than the choice. Keys are named `player_id`, `game_id`.
- **F6.3** Uniform suffixes: `_id`, `_date`, `_total`, `_num`. [SQL Style Guide](https://www.sqlstyle.guide/). *Applies to us:* `birth_date`, `game_id`. Keep nflverse stat names as-is so they stay traceable to the source. **INFERENCE:** name constraints `pk_<table>`, `fk_<table>_<ref>`, `ix_<table>_<cols>`. MySQL always names the PK `PRIMARY`, so `pk_` is documentation only.

## 7. Bulk loading and swap

- **F7.1** `LOAD DATA` "is usually 20 times faster than using INSERT statements". For INSERT, use "multiple VALUES lists". [8.4 manual, Optimizing INSERT Statements](https://dev.mysql.com/doc/refman/8.4/en/insert-optimization.html) (n.d.). *Applies to us:* prefer `LOAD DATA [LOCAL] INFILE` into staging. Batched multi-row INSERT (e.g. 1,000 rows per statement) is the fallback.
- **F7.2** `local_infile` is "disabled" by default on the server, and the client library also defaults to disabled. Both sides must allow it. [8.4 manual, Security Considerations for LOAD DATA LOCAL](https://dev.mysql.com/doc/refman/8.4/en/load-data-local-security.html) (n.d.). Non-LOCAL needs FILE and obeys `secure_file_priv`. [8.4 manual, LOAD DATA](https://dev.mysql.com/doc/refman/8.4/en/load-data.html) (n.d.). *Applies to us:* enable `local_infile` on the server and in the Node mysql2 client (`infileStreamFactory` / `LOCAL INFILE` option, **UNVERIFIED** exact option name), or use server-side files under `secure_file_priv`.
- **F7.3** Turn off autocommit for imports. You may disable `unique_checks` and `foreign_key_checks`. "it is faster to insert rows in PRIMARY KEY order". [8.4 manual, Bulk Data Loading for InnoDB](https://dev.mysql.com/doc/refman/8.4/en/optimizing-innodb-bulk-data-loading.html) (n.d.). *Applies to us:* sort each CSV by the PK before loading. Wrap the load in one transaction. Disable unique_checks only if the data was already de-duplicated.
- **F7.4** In LOAD DATA, an empty field becomes `''`, 0 or a zero date, not NULL. `\N` is read as NULL. Use `(col, @var) SET col = ...` to transform values. [LOAD DATA](https://dev.mysql.com/doc/refman/8.4/en/load-data.html). *Applies to us:* nflverse CSVs use empty cells and/or `NA` for missing values (**UNVERIFIED** per file). Map them with `SET x = NULLIF(NULLIF(@x,''),'NA')`, or the zeros will silently corrupt stats.
- **F7.5** `RENAME TABLE` is atomic: "no other session can access any of the tables". It goes left to right, so `a TO tmp, b TO a, tmp TO b` swaps two tables. FK names pointing at a renamed table are "automatically updated". Privileges are not moved. [8.4 manual, RENAME TABLE](https://dev.mysql.com/doc/refman/8.4/en/rename-table.html) (n.d.). Yet "DDL statements... implicitly end any transaction". "Atomic DDL is not transactional DDL." [8.4 manual, Atomic DDL](https://dev.mysql.com/doc/refman/8.4/en/atomic-ddl.html) (n.d.). *Applies to us:* RENAME swaps a whole table. It fits full-replace tables (player, schedules for all seasons) but cannot sit inside your "one transaction". FKs from other tables follow the renamed (old) table, which is a trap with child-table FKs.
- **F7.6** `ALTER TABLE ... EXCHANGE PARTITION ... WITH TABLE` swaps one partition with a table that has the same structure. Neither table may have FKs. `WITHOUT VALIDATION` took 0.01s versus 0.74s for 1M rows. [8.4 manual, Exchanging Partitions](https://dev.mysql.com/doc/refman/8.4/en/partitioning-management-exchange.html) (n.d.). *Applies to us:* this is the purpose-built "replace one season" operation if fact tables are `PARTITION BY LIST (season)`. It costs FKs (F2.9) and is DDL (implicit commit, F7.5).
- **F7.7 INFERENCE.** At our sizes, the simplest correct way to replace one season is a single InnoDB transaction: `START TRANSACTION; DELETE FROM t WHERE season=?; INSERT INTO t SELECT ... FROM stg_t; COMMIT;`. It is truly transactional, works with FKs, and readers see the old season until COMMIT (InnoDB MVCC, default REPEATABLE READ; not fetched here). Expect about 6k rows for player_week and about 50k for pbp. Pick EXCHANGE PARTITION only if timing shows the DELETE+INSERT is too slow.

## Recommended rule set

1. **Declare the grain** of every table in its DDL comment before writing columns. One grain per table, atomic level. Never mix season totals into weekly tables. (F1.1, F1.2, F1.3)
2. **Model entities in 3NF** (player, team, game). Treat stats, snaps, injuries, rosters and plays as fact tables keyed by entity IDs plus season/week. Roster and injury are factless or event facts. (F1.4, F1.6, F1.7, F1.8)
3. **Every table gets an explicit PK.** For facts, use the natural composite key, leading with the dominant filter: e.g. `player_week_stat PRIMARY KEY (season, season_type, week, player_id)`, `play PRIMARY KEY (game_id, play_id)`. (F2.1, F2.3, F2.5, F5.1, F5.4)
4. **Keep PKs short and fixed-width.** Use no surrogate keys unless you merge ID systems or need history. Map other IDs through a crosswalk table. (F2.2, F2.6)
5. **Give each fact table at most 1 or 2 secondary indexes**, e.g. `(player_id)`, which InnoDB auto-extends with the PK. Confirm them with EXPLAIN before adding any covering index. (F2.4, F5.2, F5.3)
6. **Declare FKs from facts to entity tables, except on season-partitioned tables.** If a load disables `foreign_key_checks`, run an explicit orphan query before committing. Leave sparse pbp player-ID columns without FKs. (F2.7, F2.8, F2.9, F2.10)
7. **Use the smallest correct integer type.** season SMALLINT UNSIGNED, week TINYINT UNSIGNED. Yards are signed SMALLINT. No display widths, ZEROFILL or `FLOAT(M,D)`. (F3.1, F3.2)
8. **Store 0/1 flags as BOOLEAN** (TINYINT(1)) and model outputs (EPA, WPA, CPOE, shares) as DOUBLE. Use DECIMAL only where exact decimal arithmetic is needed. Store counts, not just rates, so week ranges stay summable. (F1.3, F3.3, F3.4)
9. **Make ID and code columns identical everywhere**: `CHAR(10) CHARACTER SET ascii COLLATE ascii_bin` for gsis id (verify length). Use short ascii VARCHAR for team and position. Names stay utf8mb4 with the default `utf8mb4_0900_ai_ci`. (F3.5, F3.6, F3.7)
