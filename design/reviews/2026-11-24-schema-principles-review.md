## 1. Requirements: the principles, verbatim, with sources

Each row is a requirement the schema can be checked against (**R**), its **tier**, the principle **quoted verbatim** from the source, and the link. All links were fetched on 2026-11-24 and returned HTTP 200. Quotes came back through a fetch tool; spot-check wording against the live page before adopting a row as a global rule. **R33–R50** (2026-11-25): the Kimball, Kent, Codd, Airflow and PostgreSQL quotes were checked character for character against the downloaded page text (Kimball's typographic ligatures "ﬁ"/"ﬂ" are written here as plain letters). The MySQL pages refused direct download (HTTP 403), so their quotes came through a fetch tool that summarizes pages and need the same spot-check.

**Tiers.** *Foundational*: relational integrity (keys, references, grain, functional dependency); a violation is a defect. *Engine*: MySQL-specific engineering; a violation is a defect on MySQL. *Design*: a sound default that is weighed against requirements and source-data behavior; a departure is allowed when it is written down with its reason (R31).

**Sources.** **MySQL 8.4 Reference Manual** is the engine's primary documentation. **Apache Airflow** documentation is cited for re-runnable pipeline tasks (R29). **Kent (1982)** is the standard plain-language statement of the normal forms. **PostgreSQL** documentation is cited where it states a cross-engine relational principle more directly than MySQL's manual. **Kimball Group** is the reference for dimensional (fact/dimension) modeling, which the ETL spec already follows for its fact tables. **Codd's rules** are quoted from Joe Celko's article on them (Simple Talk), not from Codd's 1985 paper. Kimball **Design Tips** are the Kimball Group's own articles.

### 1.1 Keys and referential integrity

| R | Tier | Requirement | Principle, verbatim | Source |
|---|---|---|---|---|
| R1 | Foundational | Every table declares a primary key. | "Specify a primary key for every table using the most frequently queried column or columns, or an auto-increment value if there is no obvious primary key." | [MySQL: InnoDB best practices](https://dev.mysql.com/doc/refman/8.4/en/innodb-best-practices.html) |
| R2 | Engine | The primary key is the clustered index; choose its column order for the most common lookups, and keep it short. | "When you define a `PRIMARY KEY` on a table, `InnoDB` uses it as the clustered index. A primary key should be defined for each table." … "If the primary key is long, the secondary indexes use more space, so it is advantageous to have a short primary key." | [MySQL: clustered and secondary indexes](https://dev.mysql.com/doc/refman/8.4/en/innodb-index-types.html) |
| R3 | Foundational | Every column that identifies a row of another table carries a foreign key to it, with the same data type on both sides. | "Use joins wherever data is pulled from multiple tables based on identical ID values from those tables. For fast join performance, define foreign keys on the join columns, and declare those columns with the same data type in each table." | [MySQL: InnoDB best practices](https://dev.mysql.com/doc/refman/8.4/en/innodb-best-practices.html) |
| R4 | Foundational | Foreign keys are how referential integrity is maintained. | "A foreign key constraint specifies that the values in a column (or a group of columns) must match the values appearing in some row of another table. We say this maintains the *referential integrity* between two related tables." … "Making correct use of foreign keys will definitely improve the quality of your database applications, so you are strongly encouraged to learn about them." | [PostgreSQL: constraints](https://www.postgresql.org/docs/current/ddl-constraints.html); [PostgreSQL: foreign keys tutorial](https://www.postgresql.org/docs/current/tutorial-fk.html) |
| R5 | Engine | A foreign key's referenced columns are a primary key or unique key (MySQL default); design the parent accordingly. | `restrict_fk_on_non_standard_key`, default `ON`: "This variable, when `ON` (the default), prevents the use of non-unique keys or partial keys as foreign keys." The override is deprecated. | [MySQL: server system variables](https://dev.mysql.com/doc/refman/8.4/en/server-system-variables.html#sysvar_restrict_fk_on_non_standard_key) |
| R6 | Engine | Expect the engine to index the child side of every foreign key; don't duplicate those indexes. | "MySQL requires indexes on foreign keys and referenced keys so that foreign key checks can be fast and do not require a table scan." … "Such an index is created on the referencing table automatically if it does not exist." | [MySQL: FOREIGN KEY constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html) |
| R7 | Engine | Design loads knowing MySQL checks foreign keys per statement, not at commit: a referenced parent row cannot be deleted while children exist, even inside a transaction that re-inserts it; children are deleted before parents and inserted after them. | "MySQL checks foreign key constraints immediately; the check is not deferred to transaction commit." … "Since MySQL does not support deferred constraint checking, `NO ACTION` is treated as `RESTRICT`." | [MySQL: foreign key constraint differences](https://dev.mysql.com/doc/refman/8.4/en/ansi-diff-foreign-keys.html); [MySQL: FOREIGN KEY constraints](https://dev.mysql.com/doc/refman/8.4/en/create-table-foreign-keys.html) |
| R8 | Foundational | Rules that span rows or tables are declared as `UNIQUE` or `FOREIGN KEY` constraints, not left to application code. `CHECK` covers single-row rules only. | "If possible, use UNIQUE, EXCLUDE, or FOREIGN KEY constraints to express cross-row and cross-table restrictions." (MySQL has no `EXCLUDE`; on MySQL this means `UNIQUE` and `FOREIGN KEY`.) Codd, Rule 10: "Integrity constraints specific to a particular relational database must be definable in the relational data sublanguage and storable in the catalog, not in the application programs." | [PostgreSQL: constraints](https://www.postgresql.org/docs/current/ddl-constraints.html); [Codd's rules (Celko, Simple Talk)](https://www.red-gate.com/simple-talk/databases/theory-and-design/codds-twelve-rules/) |

### 1.2 Normalization and table structure

| R | Tier | Requirement | Principle, verbatim | Source |
|---|---|---|---|---|
| R9 | Foundational | **1NF.** Every row of a table has the same fields; a variable-length list is never packed into one row. | "Under first normal form, all occurrences of a record type must contain the same number of fields." … "First normal form excludes variable repeating fields and groups." | [Kent: A Simple Guide to Five Normal Forms](https://www.bkent.net/Doc/simple5.htm) |
| R10 | Foundational | **2NF.** Every non-key column is a fact about the whole key. | "Second normal form is violated when a non-key field is a fact about a subset of a key." | [Kent](https://www.bkent.net/Doc/simple5.htm) |
| R11 | Foundational | **3NF.** No non-key column is a fact about another non-key column. A player's name is a fact about the player, not about the player-week. | "Third normal form is violated when a non-key field is a fact about another non-key field". Summary: "a non-key field must provide a fact about the key, us[e] the whole key, and nothing but the key." | [Kent](https://www.bkent.net/Doc/simple5.htm) |
| R12 | Foundational | Keep data non-redundant; replace repeated descriptive values with an ID that joins to one row. Redundancy is what normalization exists to prevent. | "Normally, try to keep all data nonredundant (observing what is referred to in database theory as third normal form)." … "Instead of repeating lengthy values such as names and addresses, assign them unique IDs". Kent: "The normalization rules are designed to prevent update anomalies and data inconsistencies." | [MySQL: data size](https://dev.mysql.com/doc/refman/8.4/en/data-size.html); [Kent](https://www.bkent.net/Doc/simple5.htm) |
| R13 | Design | Each entity has one table holding that entity and its properties; fact tables hold keys, measures and degenerate dimension values. | "a fact table always contains foreign keys for each of its associated dimensions" … "optional degenerate dimension keys and date/time stamps." Dimension tables hold the descriptions: "Dimension tables are usually wide, flat denormalized tables with many low-cardinality text attributes." | [Kimball: fact table structure](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/fact-table-structure); [Kimball: dimension table structure](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/dimension-table-structure) |
| R14 | Foundational | Each fact table has one declared grain, and grains are never mixed. | "Declaring the *grain* is the pivotal step in a dimensional design." … "Each proposed fact table grain results in a separate physical table;" … "different grains must not be mixed in the same fact table." | [Kimball: grain](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/grain/) |
| R15 | Design | A many-to-many between a fact and a dimension (several players in one role on one play) goes through a bridge table rather than numbered column slots. | "the multivalued dimension must be attached to the fact table through a group dimension key to a bridge table". | [Kimball: multivalued dimensions and bridge tables](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/multivalued-dimension-bridge-table) |
| R16 | Design | A fact that references a dimension member not yet known gets a placeholder dimension row, filled in later; the fact is not dropped. | "In these cases, special dimension rows are created with the unresolved natural keys as attributes." … "the placeholder dimension rows are updated with type 1 overwrites." | [Kimball: late arriving dimensions](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/late-arriving-dimension/) |
| R17 | Design | A dimension attribute whose history matters is tracked deliberately: either as a new dimension row (type 2), or as a fact of the event at the fact's grain (a player's position *that week* depends on the whole player-week key, so it satisfies R10). It is not copied from the current dimension row. | "Slowly changing dimension *type 2* changes add a new row in the dimension with the updated attribute values." | [Kimball: type 2](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/type-2/) |
| R31 | Design | Full normalization is the default; a departure for a documented performance or usability reason is allowed, and the reason is written down. | "There is no obligation to fully normalize all records when actual performance requirements are taken into account." … "the desirability of normalization has to be assessed, in terms of its performance impact on retrieval applications." | [Kent](https://www.bkent.net/Doc/simple5.htm) |

### 1.3 Column types and nullability

| R | Tier | Requirement | Principle, verbatim | Source |
|---|---|---|---|---|
| R18 | Engine | Use the smallest type that holds the data. | "Use the most efficient (smallest) data types possible." … "`MEDIUMINT` is often a better choice than `INT` because a `MEDIUMINT` column uses 25% less space." | [MySQL: data size](https://dev.mysql.com/doc/refman/8.4/en/data-size.html) |
| R19 | Foundational | Declare `NOT NULL` wherever the column's meaning requires a value **and** the source guarantees one; decide per column, never by blanket rule in either direction. | "Declare columns to be `NOT NULL` if possible. It makes SQL operations faster, by enabling better use of indexes". … "In most database designs the majority of columns should be marked not null." | [MySQL: data size](https://dev.mysql.com/doc/refman/8.4/en/data-size.html); [PostgreSQL: constraints](https://www.postgresql.org/docs/current/ddl-constraints.html) |
| R20 | Engine | Prefer numeric columns for IDs and codes that can be numeric. | "For unique IDs or other values that can be represented as either strings or numbers, prefer numeric columns to string columns." | [MySQL: optimizing for numeric data](https://dev.mysql.com/doc/refman/8.4/en/optimize-numeric.html) |
| R21 | Engine | `ENUM` is for closed, stable value sets. Remember it sorts by declaration order. Where the set is expected to grow or the UI needs labels, use a lookup table with a foreign key. | "`ENUM` values are sorted based on their index numbers" … "Using `ENUM` columns in `ORDER BY` clauses requires extra care". | [MySQL: ENUM](https://dev.mysql.com/doc/refman/8.4/en/enum.html) |
| R22 | Engine | Choose `DATETIME` or `TIMESTAMP` deliberately: `TIMESTAMP` converts through the session time zone and ends in 2038; `DATETIME` does neither. | "MySQL converts `TIMESTAMP` values from the current time zone to UTC for storage, and back from UTC to the current time zone for retrieval. (This does not occur for other types such as `DATETIME`.)" … "`TIMESTAMP` has a range of `'1970-01-01 00:00:01'` UTC to `'2038-01-19 03:14:07'` UTC." | [MySQL: DATE, DATETIME, TIMESTAMP](https://dev.mysql.com/doc/refman/8.4/en/datetime.html) |
| R23 | Engine | Stay inside the engine's row and column limits, counting `VARCHAR` at its declared maximum in the column's charset; and within the limit of 64 indexes per table, since every foreign key needs an index. | "InnoDB has a limit of 1017 columns per table." … "has a maximum row size limit of 65,535 bytes" … "the maximum row size is slightly less than 8KB for the default 16KB `InnoDB` page size." Observed on MySQL 8.4 (2026-11-27), adding foreign keys on every player and team column of `play`: "Too many keys specified; max 64 keys allowed" (error 1069). | [MySQL: column count and row size limits](https://dev.mysql.com/doc/refman/8.4/en/column-count-limit.html) |

### 1.4 Indexes

| R | Tier | Requirement | Principle, verbatim | Source |
|---|---|---|---|---|
| R24 | Engine | Every access path the application uses has an index whose leftmost columns match the filter; confirm with the query plan before adding more. | "If the table has a multiple-column index, any leftmost prefix of the index can be used by the optimizer to look up rows." … "MySQL cannot use the index to perform lookups if the columns do not form a leftmost prefix of the index." | [MySQL: multiple-column indexes](https://dev.mysql.com/doc/refman/8.4/en/multiple-column-indexes.html) |

| R | Tier | Requirement | Principle, verbatim | Source |
|---|---|---|---|---|
| R26 | Design | Lowercase, consistent identifiers; one name per concept across tables, and different names for different concepts. | "it is best to adopt a consistent convention, such as always creating and referring to databases and tables using lowercase names. ### 1.6 Load semantics and change tracking

| R | Tier | Requirement | Principle, verbatim | Source |
|---|---|---|---|---|
| R28 | Design | Rows record when they were created and last changed, so corrections are visible per row. This only works if the load updates rows in place; a load that deletes and re-inserts resets both. | Kimball: "it is helpful to create an *audit dimension* containing the ETL processing metadata known at the time", including "the ETL process execution time stamps". MySQL: "An auto-updated column remains unchanged if all other columns are set to their current values." | [Kimball: audit dimension](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/audit-dimension/); [MySQL: TIMESTAMP initialization](https://dev.mysql.com/doc/refman/8.4/en/timestamp-initialization.html) |
| R29 | Design | Loads are idempotent: running the same load twice on the same input leaves the same data. Transactional delete-and-replace and upsert both meet this; choose between them by what else is needed (row-level change tracking needs upsert, R28). | "You should treat tasks in Airflow equivalent to transactions in a database. This implies that you should never produce incomplete results from your tasks." … "Airflow can retry a task if it fails. Thus, the tasks should produce the same outcome on every re-run." (The same page goes on to prescribe UPSERT over INSERT, but delete-and-replace inside a transaction also meets the requirement.) | [Apache Airflow: best practices](https://airflow.apache.org/docs/apache-airflow/stable/best-practices.html) |
| R32 | Engine | When loading by upsert, use `INSERT … ON DUPLICATE KEY UPDATE`, which leaves unchanged rows unwritten and reports what changed; avoid it on tables with more than one unique key; never use `INSERT IGNORE` for idempotency, because it also silences NULL, duplicate and foreign-key errors. | "the affected-rows value per row is 1 if the row is inserted as a new row, 2 if an existing row is updated, and 0 if an existing row is set to its current values." … "In general, you should try to avoid using an `ON DUPLICATE KEY UPDATE` clause on tables with multiple unique indexes." `IGNORE` downgrades to warnings, among others, `ER_BAD_NULL_ERROR`, `ER_DUP_ENTRY`, `ER_NO_REFERENCED_ROW_2`. | [MySQL: INSERT … ON DUPLICATE KEY UPDATE](https://dev.mysql.com/doc/refman/8.4/en/insert-on-duplicate.html); [MySQL: the effect of IGNORE](https://dev.mysql.com/doc/refman/8.4/en/sql-mode.html#ignore-effect-on-execution) |
| R30 | Engine | Group related writes in explicit transactions; lock rows with `SELECT … FOR UPDATE`, never `LOCK TABLES`. | "Group sets of related DML operations into transactions by bracketing them with `START TRANSACTION` and `COMMIT` statements." … "Do not use `LOCK TABLES` statements." … "To get exclusive write access to a set of rows, use the `SELECT ... FOR UPDATE` syntax to lock just the rows you intend to update." | [MySQL: InnoDB best practices](https://dev.mysql.com/doc/refman/8.4/en/innodb-best-practices.html); [MySQL: locking reads](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html) |

### 1.7 Integrating identifiers from several sources (revision 6)

| R | Tier | Requirement | Principle, verbatim | Source |
|---|---|---|---|---|
| R33 | Foundational | An entity that several source systems identify differently has one master key. Every source's ID for it is mapped to that key in one table, tagged with its source so IDs from different providers can't collide, and the loads read that table. | "Dealing with duplicate entries in a dimension, or integrating disparate sources into a single dimension, involves more complex business logic that relies on durable keys." … "you might need to mark the natural keys from the different sources so they don’t collide with each other. Try using a character data type for the source natural key, prepended by a source code." … "This table then becomes input to the dimension and fact managers." Also: "natural keys for a dimension may be created by more than one source system, and these natural keys may be incompatible or poorly administered." | [Kimball Design Tip #147: durable "super-natural" keys](https://www.kimballgroup.com/2012/07/design-tip-147-durable-super-natural-keys/); [Kimball: dimension surrogate keys](https://www.kimballgroup.com/data-warehouse-business-intelligence-resources/kimball-techniques/dimensional-modeling-techniques/dimension-surrogate-key/) |
| R34 | Foundational | One thing has one identifier, written the same way in every table. | "Functional dependencies only exist when the things involved have unique and singular identifiers (representations)." … "We are not defending the use of non-unique or non-singular representations. Such practices often lead to data maintenance problems of their own." | [Kent](https://www.bkent.net/Doc/simple5.htm) |
| R35 | Foundational | Information is stored as values in tables, in one place. Which provider an ID belongs to is a value, not part of a column name, and one ID is not stored under two names. | Codd, Rule 1: "All information in a relational database is represented explicitly at the logical level and in exactly one way – by values in tables." | [Codd's rules (Celko, Simple Talk)](https://www.red-gate.com/simple-talk/databases/theory-and-design/codds-twelve-rules/) |

### 5.2 Open, in plain terms

Each entry: **the question**, **why it matters**, **the options** and what each would mean in practice, and **Claude's recommendation** (yours to accept or reject).

**Decided questions** (their options and evidence, as put to the owner, are in Appendix C): O1 roster rows for players missing from `players.csv` → D5; O2 snap counts → D4; O3 overlapping runs → D1; O4 player foreign keys in `play` and `game` → D3, D8; O5 load method → D9; O6 row timestamps → D10; O7 `play_participant` → D8 (revised: columns kept); O9 weekly position → D7; O11 one ID per provider → D4; O12 unidentifiable players → D5.

**O5. Should fact tables be loaded by upsert instead of delete-and-replace?** *Decided by the owner, 2026-11-27: upsert for every table, never delete-and-replace, plus a quarterly reconciliation of removed rows (D9, ADR-0028).*
- *Why it matters:* today every fact table (weekly stats, rosters, injuries, snap counts, depth charts, plays) is loaded by deleting the season's rows and re-inserting the whole file. That rewrites every row each time, resets any `created_at`/`updated_at` (O6 depends on this), and removes rows the source dropped. Upsert writes only new and changed rows (R29) but keeps rows the source dropped, so a dropped row needs its own rule.
- *Options:* (a) keep delete-and-replace for all fact tables; (b) upsert all fact tables, keeping rows the source dropped; (c) upsert, then delete rows in the piece's scope that weren't in the file: an exact copy of the file, but only changed rows are touched.
- *Recommendation:* (c) for every fact table, `depth_chart` included: nothing establishes that a published snapshot is never corrected. The scope of the delete step is the piece (one season for history tables). For `play` and `depth_chart`, which keep the current season only (ADR-0013), the load also deletes every earlier season's rows, so season rollover still empties the old season. (c) keeps each table an exact copy of the source and makes O6 meaningful.

**O6. Add `created_at` and `updated_at` to every data table (P1)?** *Decided by the owner, 2026-11-27: yes, every table, set by the database (D10, ADR-0029).*
- *Why it matters:* without them there is no way to tell which rows nflverse corrected, or when a row first appeared. With them, "which stat lines changed in last night's load" is one query.
- *Options:* yes (needs O5 (b) or (c) to be meaningful) / no / only on tables loaded by upsert.
- *Recommendation:* yes, together with O5, and with every database session set to UTC (P1), since MySQL fills these columns from the session's clock.

**O8. How should `NOT NULL` be decided (P4)?**
- *Why it matters:* today nothing but key columns is required, so a load with a missing game week or team code succeeds silently. The opposite rule (require everything the profile never saw empty) already failed once: live data broke it in 2026-11.
- *Options:* (a) per column by meaning and source guarantee (P4), producing a reviewed list; (b) keep everything non-key nullable.
- *Recommendation:* (a). Claude drafts the list; you approve it.

**O10. Small consistency fixes?** *(c) decided by the owner, 2026-11-27: keep the ledger write inside the data's transaction (ADR-0006). (e) decided by the owner, 2026-11-27: leave SQL mode as it is (MySQL 8.4's default, which is strict); no change.*
- *Why it matters:* low risk now, more costly once the API exposes these names.
- *Options, each yes/no:* (a) rename `headshot` → `headshot_url` and `opponent` → `opponent_team` (W2); (b) add a database creation script that declares `utf8mb4` / `utf8mb4_0900_ai_ci` (W3); (c) confirm the ledger write inside the swap transaction (Claude's change, already built, never confirmed); (d) declare `ON DELETE RESTRICT` explicitly on every fact-to-dimension foreign key (R41); (e) set strict SQL mode on every pipeline session, and check the host's setting with `SELECT @@GLOBAL.sql_mode` (R46).
- *Recommendation:* yes to all five.

## Appendix C. Decided questions as they were put (O1–O4, O7, O9, O11, O12)

Kept for the options and evidence behind each decision. Decision numbers are the consolidated ones (§5.1).

**O1. A roster row names a player the `player` table doesn't have: load it or skip it?** *Decided by the owner, 2026-11-25: (b), excluded during transform; recorded as D5. Claude's recommendation below changed from (a) to (b) after the 2025 roster showed who these players are.*
- *What's happening:* these players **are** on rosters; they appear in nflverse's roster files. What they lack is an entry in nflverse's player file (`players.csv`), which fills our `player` table. Once `roster.gsis_id` must point at a real `player` row (D3), each such roster row either gets a `player` row to point at or can't load. Live database, 2026-11-25 (checks 9–11): 858 roster rows, 806 players, 154–201 per season for 2022–2026. **No other table references any of them**: zero weekly stat rows, plays, games, injury reports or depth-chart rows. (The earlier "1,610 rows" came from source-file profiling back to 2017.)
- *Options:* (a) **Placeholder from the roster row:** create the missing `player` row from the roster row's own identity columns (names, birth date, college, height, weight; provider IDs as `player_source` rows, D4), so the roster row loads; if `players.csv` later lists him, the next player load overwrites it. Cost: 806 extra `player` rows for players with no stats in our data, so the player list and search should show only players with stats or a current roster spot. (b) **Skip:** leave the roster row out and log the count. Cost: about 150–200 true roster entries per season are lost (the roster file says the player was on that team). A current-season player is picked up once `players.csv` lists him, because the current season reloads; a past season, loaded once, keeps the gap. (c) **Split:** skip on `roster`, as (b); placeholder on the fact tables (`player_week_stat`, `play`, `injury_report`, …), as (a), where skipping would drop a real stat line. No fact-table rows need it today.
- *Recommendation:* (a), on every table. It is R16: a row that references an unknown player keeps the row and adds the player. The roster row already holds the identity columns, so the new `player` row is nearly complete, not a bare ID; and it lets P2 drop `roster`'s identity columns without losing these 806 players. (b) and (c) are simpler but drop true roster entries, an exception to R16 that would need your explicit approval. Parents still load first (`team`, then `player` and `game`, then facts); there are no game placeholders, so `game` must load before any table that references it.

**O2. How does a snap count point at a player?** *Decided by the owner, 2026-11-25: (b), recorded as D4. Claude had recommended (a).*
- *The two IDs:*
  - `gsis_id` is the NFL's own player ID, from its Game Stats and Info Service (format `00-00#####`). nflverse keys everything on it: its dictionary calls it the "Primary key for all data" (data dictionary A5). It is `player`'s primary key, and every player reference in `roster`, `player_week_stat`, `injury_report`, `depth_chart`, `play` and `game` is a `gsis_id`.
  - `pfr_id` (for example `MahoPa00`) is Pro Football Reference's ID: one website's identifier. nflverse has it because its snap counts come from that site; `players.csv` carries it as a cross-reference. 8.7% of players in `players.csv` have none, and 47.4% of roster rows (data dictionary A5, A6), so it can't be a primary key. Under D4 it becomes a `player_source` row with `source_code = 'pfr'`.
- *Why it matters:* `snap_count` is the only table that names players by `pfr_id`. Live (checks 4, 6, 7): no `pfr_id` is shared by two players; 14 PFR IDs (143 snap rows) match no player, and the rosters can't resolve any of them.
- *Options (revised for D4):* (a) **Resolve at load:** look up each snap row's PFR ID in `player_source` (`source_code = 'pfr'`), store the `gsis_id` in a new `snap_count.gsis_id` column with a foreign key to `player`, and keep `pfr_player_id` as the source's own key. The 143 unmatched rows load with an empty `gsis_id` (O12). (b) **Composite foreign key** from `snap_count (source_code, pfr_player_id)` to `player_source`'s unique key: needs a constant `source_code` column on every snap row, and the player is still one join away. The earlier option, a unique `player.pfr_id`, ended with D4.
- *Recommendation:* (a). It is R36: the load swaps the source's key for the master key, so every player reference in the database is a `gsis_id`.

**O3. What happens if two runs load the same data at the same time?** *Decided by the owner, 2026-11-25: (a), plus up to 2 retries of a failed publishing transaction, with logging; recorded as D1. Claude had recommended (b), then changed to (a) once it was clear overlapping runs almost always load the same file version.*
- *Why it matters:* after D1, nothing stops two runs from overlapping (a manual backfill during the scheduled run, or two server instances). Each load is all-or-nothing, so you never get half a file or duplicates. What isn't guaranteed is that the **newer download wins**: if run A downloads first, run B downloads later (possibly a newer file) and commits, then A commits its older copy over B's. The ledger row commits with the data, so it records A's version; the next run that sees a different version on the server reloads it. How soon that is depends on the schedule (§9), not on a fixed interval. A second, smaller gap: a run that fails writes `failed` to the ledger outside any transaction and can overwrite another run's `loaded` status.
- *Options:*
  - (a) **Accept it**, as above.
  - (b) **Version check at publish** (optimistic concurrency). Each piece's ledger row carries a `publish_version` number that every successful load increments. An attempt reads it before downloading (creating the ledger row at version 0 if the piece has never loaded). Inside the swap transaction it locks the ledger row (`SELECT … FOR UPDATE`, R30; for `play` and `depth_chart`, whose load replaces the whole table, every ledger row of the dataset) and publishes only if the version is unchanged; the commit increments it and releases the lock. If another run published in between, the attempt rolls back, is recorded as superseded (not failed), and retries the piece once from the HEAD request: if the other run already loaded the current file, the `ETag` check skips it; otherwise it downloads the newer file and publishes. A second loss is recorded as superseded and left to the next scheduled run. Status writes (`downloading`, `failed`) carry the same condition (`WHERE publish_version = ` the version read at the start), so a failed or stale attempt never overwrites a newer successful load's status. Adds one ledger column (§4 2b) and needs 2a: the `ETag` skip must compare against the last *successful* load's `ETag`, because today's ledger overwrites `source_etag` when each attempt starts. Assumes nothing about clocks or about the order a CDN serves file versions in. Proposed by ChatGPT (2026-11-24); replaces Claude's revision 3 design, which compared download times and needed both of those assumptions.
  - (c) **One run at a time**: brings back a run lock, which D1 removed.
- *Recommendation:* (b). It is the standard optimistic-concurrency pattern: no run lock (D1 stands), no clock comparison, and losing costs one extra HEAD request when the winner already loaded the current file. The retry fits D1's remedy (idempotent loads plus retry).

**O4. Which player columns in `play` and `game` get foreign keys?** *Decided by the owner, 2026-11-25: all of them (D3). The `play_participant` part was revised on 2026-11-27: the numbered columns stay, each player column with a foreign key (D8).*

Live (check 11, 2026-11-25): all 48 `play` columns and both `game` QB columns reference only players that exist, so every one of these foreign keys would load today with no placeholders.
- *Options:* (a) all of them; (b) only the ones the app uses (`game`'s two QB IDs; `play`'s passer, rusher, receiver); (c) adopt `play_participant` (O7), which turns the 22 slot columns into one foreign key, then put foreign keys on all 26 single-role columns and `game`'s two.
- *Recommendation:* (c), or (a) if O7 is declined. (b) would contradict D3, which requires player references to carry foreign keys, not just the ones used today.

**O11. Can a player have more than one ID at the same provider?** *Decided by the owner, 2026-11-25: (a), recorded as D4.*
- *Why it matters:* P6's primary key `(gsis_id, source_code)` allows one. If a provider reissues a player's ID, or two files disagree, the load must pick one.
- *Live evidence (nflverse 2025 files, 2026-11-25):* within the roster file, no player has two ESPN, Sleeper, Yahoo, Sportradar or PFR IDs, and none of those IDs belongs to two players. - *Recommendation:* (a). The data is one-to-one apart from 6 conflicts, and league imports need one answer per provider. Revisit if a provider is seen reissuing IDs.

**O12. A row whose player can't be identified: empty reference or an "unknown player" row?** *Decided by the owner, 2026-11-25: (a), recorded as D5.*
- *What's happening:* 143 snap rows carry a PFR ID no player has; 24,076 depth-chart rows have no `gsis_id` (22,826 of them carry a name). Under D3 the foreign key must accept them, or they can't load.
- *Options:* (a) **Empty (NULL) reference**, keeping the source's own key on the row (`pfr_player_id`; `depth_chart.espn_id` and name), counting such rows on every load (R49), and filling the reference on a later load once the player appears (R38's reprocessing). (c) **Leave them out, logged:** drops real rows, an exception to R16 and R38 that would need your approval.
- *Other links, tested on the 2025 files (2026-11-25):* four other paths can connect such a row to a player. Only the first is an exact ID match from nflverse's own player file; the rest are a different file's ID, a third-party crosswalk, or a name match.
  1. **`players.csv` ESPN ID** (through `player_source`): resolves 393 of the 5,577 depth-chart rows without a `gsis_id` (E4).
  2. **The roster file's ID columns:** resolve 221 more depth-chart rows, all Chris Manhertz, whose roster ESPN ID conflicts with `players.csv` and is therefore logged, not stored (D4, E5). No unmatched snap ID resolves this way.
  3. **The DynastyProcess ID crosswalk** (`db_playerids.csv`, a third-party file nflverse distributes): resolves 2 snap players and 145 depth-chart rows, but to `gsis_id`s that `players.csv` doesn't have (E3, E8), so they would also need placeholder players (O1). Not one of today's sources.
  4. **Name matching within a narrow scope:** same game, team and exact name in the weekly stats resolves 3 of the 6 unmatched snap IDs (E2). - *Recommendation:* (a). Resolve automatically only by exact ID through `player_source` (path 1). Roster IDs that D4 rejects, the third-party crosswalk and name matches are not applied automatically: each fails in at least one example above. Every unresolved row keeps its source key and name and is counted on each load. Each case in §5.4 can get its own fix later. A NULL reference says plainly what is unknown; an "unknown" row mainly serves reporting tools that can't handle NULL joins.
